### Must fix

1. `src/core/db/backup.ts:114` - **a trigger named `sqlite_stat1` slips past the restore check.** `schemaOf` leaves out every schema entry named `sqlite_stat1` to `sqlite_stat9`, whatever its type, so ANALYZE's tables do not count as "extra". SQLite does not refuse reserved names when it loads a file's schema, so a crafted file can hold a trigger (or view) with that name. Confirmed with a throwaway test: a real backup, plus `CREATE TRIGGER evil AFTER INSERT ON transactions BEGIN UPDATE transactions SET excluded = 1 WHERE id = NEW.id; END`, renamed to `sqlite_stat1` with `PRAGMA writable_schema` (opened with `new DatabaseSync(path, { defensive: false })`). `checkBackup` accepted the file; after `openDatabase` and `migrate`, a new row came in ignored. On a restored profile every later sync's rows would quietly stop counting as spending (or have their amounts changed), which is what spec 39's "anything extra, such as a trigger or view the app never made, refuses the file" is there to stop. Fix: the app never runs ANALYZE (no `ANALYZE` or `PRAGMA optimize` anywhere in `src`), so drop the filter and compare every entry. If stat tables are ever needed, skip only `type = 'table'` entries with exactly the SQL SQLite writes for them. Add the renamed trigger to `backup.test.ts`.

2. `src/core/ledger/budgets.ts:153` - **lowering a budget is refused when its parent is already over, and the window offers to raise the parent.** Everything saved on the Budgets page keeps the rules, but two normal paths leave a parent's children adding up to more than the parent: budgets saved before this wave (spec 27 had no nesting rule), and moving a budgeted category on the Categories page (`src/core/ledger/categories.ts:74` checks only depth and kind). From there `budgetProblem` refuses any value above the room, also a lower one. Confirmed with a throwaway test:
   - Food ₪1,000 holding Groceries ₪800 and Restaurants ₪600 (as spec 27 allowed). Lowering Restaurants to ₪500 is refused: "Food has ₪200 left for Restaurants. Raise Food to ₪1,300 too?"
   - Total ₪1,500, Food ₪1,000 holding Restaurants ₪600, Shopping ₪500. Moving Restaurants to the top makes the split ₪2,100. Lowering Shopping to ₪400 is refused (`over_total`, room -₪100) with an offer to raise the total to ₪2,000.

   A user who wanted less is pushed to set more, and "Raise both" does it. Fix: refuse `over_parent` and `over_total` only when the new value puts more under the limit than the category does now (its current budget, or `inside` when it has none), so a change that does not make things worse always saves. Add both cases to `budgets.test.ts`. Whether a move on Categories should be refused or warned about when it breaks a budget is the owner's call: write that question in `docs/BACKLOG.md` in place of the line at `:12` ("A budget can sit inside another budget's category ... decide whether the window should warn"), which spec 37 has answered (nesting is now the design).

### Good

- Spec 39's check follows the spec's order on a private copy (`COPYFILE_EXCL`, 0600, a `.db` name so "Delete everything" finds a leftover) and builds the expected schema by replaying the file's own migrations in the order it ran them. The tests cover the hard cases: the owner's step-by-step migrated database, migrations run out of order, an extra trigger, view and table, a trigger changed under its own name, a newer app's backup. No path crosses IPC (main keeps it; the window gets only a file name), logs hold counts only, and backup and CSV refuse the data folder.

Refusals are fixed problems, raises run in one transaction and fail as a whole, money stays integer agorot end to end, and the 3-month averages are rounded to whole shekels in core.

The chooser reuses `toggleTick` and `useRoving`, and `roving.ts` gained a tested `skip` for disabled lines instead of a second helper.
