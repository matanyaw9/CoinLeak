### Must fix

1. `src/core/rules/queries.ts:213` - **ticking a row back hands your own choice to the rule.** When a row that is a rule's exception gets ticked again, `giveBack` makes it a rule-set row whenever it already has the rule's category (or the rule's Ignore). It cannot tell a row the rule had set (the case it was written for) from one you set by hand. Scenario, confirmed with a throwaway test (deleted, nothing committed): you put "Landwer TLV" in Coffee by hand; you make a "Landwer → Coffee" rule; in the editor you untick that row and save; later you tick it back (or click the box above the list, which ticks every row) and save. The row now counts as set by the rule. Delete the rule, or change what it matches, and the row loses Coffee and lands in Needs review, while the same row never unticked keeps Coffee. A row you ignored by hand behaves the same way and would count as spending again. This breaks "user edits win". Two ways to fix:
   - Simplest: drop `giveBack`. A ticked-back row loses its exception and stays yours, with the same category, so nothing on screen changes. If the rule's category later differs, the editor lists the row as "Set by you" and ticked, like any hand-set row (F45). Trade-off: after a rule delete such a row keeps its category instead of clearing, the safe side. The test at `save.test.ts:191` then needs a new expectation.
   - Exact spec behavior: remember in `rule_exceptions` which rows `keepForUser` changed (a new migration 0017, since 0016 may already be in the owner's profile) and give back only those.

   Either way, add the hand-set case above to `save.test.ts`.
