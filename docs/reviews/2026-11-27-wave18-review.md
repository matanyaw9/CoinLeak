## Should fix

1. **The guard stops Undo from bringing back an older rule (confirmed).** `src/core/rules/validate.ts:92`.
   - What happens: the check sits in `cleanTextCondition`, which every path through `cleanRuleInput` uses: save, the on/off switch (`rules:update`), the Demo, and `restoreRule`, the Undo of a delete.
   - Failure case: the owner saved `(\d+)+$` before this wave, and it sorts "order 12345" into Groceries. They delete the rule, and the row becomes uncategorized, as it should. They press Undo, and core answers `BAD_REQUEST`. The rule and the row's category are both gone, and the toast says "Something went wrong."
   - The backlog already accepts that switching such a rule off needs its pattern fixed first. Undo failing after a delete is worse: the toast offers a way back, and it does not work.
   - Fix: take the check out of `cleanTextCondition`. Call it from `saveRule` only for pattern values the stored rule does not already have, and from `previewRule` for those same new values. `restoreRule` and `createRule` then skip it. This also makes the on/off switch work again, so that backlog line can go. Add a test: insert an old risky rule, delete it, Undo, and the rule and the row's category are back.

## The three places you asked about

**Card-bill Undo (`src/core/ledger/card-bills.ts`, `restoreInternal`).** No state is written that never existed, and it never fights the matcher.
- `before` is read inside the same transaction, before the update, so it is the true earlier state.
- A row the matcher owned goes back with `internal_by_user = 0`. That makes it open, so `applyCardBills` decides its state again in the same transaction, and the link written back is replaced at once. That is the review's case: the bill is paired again and the second line is flagged again (tested).
- A row the user had marked gets its mark and its link back, and with them the card rows it used up. That is exactly the state before the answer.
- Card rows deleted for good meanwhile are handled by the `card_bill_txn_id` subquery (tested).
- Only an Undo after a later edit to the same row (for example, it was ignored in between) writes old card fields onto the new state. That is the same as `restoreExclusions` today, and the matcher still decides every open line.

**Quit during a sync (`src/main/index.ts`, `src/main/sync-service.ts`).** No hang, and no lost save.
- The first quit is held, the sync is cancelled, and the app quits on `whenStopped()` or after 20 s, whichever comes first. A second quit goes through at once (`waiting`).
- `ended` resolves in `start`'s `finally`, so a sync that fails or is cancelled always ends it. Cleanup is bounded: closing the browser takes 15 s at most, and deleting the profile about 2 s.
- A save cannot be cut in half: `ingest` is synchronous, so a quit lands before it or after it.
- If the download already finished when Quit is pressed, the abort listener is gone (`browser.ts` `finally`), so the rows are saved. The database now closes on `will-quit`, not when the window closes, so that save still has a database to write to.
- Progress events after the window is gone are guarded (`isDestroyed`).
- The start sweep skips screenshot runs. The dev-and-installed clash is in the backlog.

**Donut and bars data (`src/core/ledger/period.ts`).** The list and the middle always add up.
- `donut.groups` is `spendingByParent`, which reads the same rows, dates and flows as `totals`, uncategorized included. So the list's sum equals `spending` exactly, in agorot (whole numbers, no rounding).
- The ring is only the positive groups, with shares of `ringTotal`, so the shares make 100%.
- In each bar, `parts` plus `other` equals `drawn`, and `drawn` plus the `back` amounts equals the month's spending. Every group that gave money back in any month is in `groups`, so its money back always has a name in the tooltip and the legend.
- The only gap is display rounding: amounts show in whole shekels, so a long list can look ₪1 or ₪2 off the middle. That was so before this wave too.
